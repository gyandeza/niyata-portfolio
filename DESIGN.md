# Niyata DESIGN.md

## Visual world
**Operational Field Instrument**

Niyata should feel like a well-designed operating instrument made by someone who understands field reality, systems and management decisions.

The visual system is not a generic tech portfolio, not an agency landing page, and not a dark-mode developer console.

## Surface modes

### Experience — portfolio and case studies
Purpose: let the work lead.

Use:
- strong editorial sequencing
- large declarative typography
- evidence-led case narratives
- system diagrams
- asymmetry with disciplined grids
- clear boundaries between verified facts, assumptions and limitations

Avoid:
- feature-card soup
- decorative dashboards
- fake social proof
- generic “innovative / cutting-edge” copy
- equal visual weight for every element

### Operate — interactive tools and demos
Purpose: complete a task and understand the consequence.

Use:
- one primary decision output
- inputs grouped by decision logic
- visible formula / assumptions
- functional status colors
- immediate feedback
- explicit prototype / validation status

Avoid:
- hiding the model behind an attractive score
- nested cards
- animation that competes with task completion
- decorative risk colors

## Core palette

- Paper: `#F3F1EA`
- Paper deep: `#E9E5DB`
- Ink: `#111310`
- Dark: `#101613`
- Muted: `#676A62`
- Line: `#C9C6BC`
- Emerald: `#147A5B`
- Emerald bright: `#45B987`

Functional colors, only when meaning is operational:
- Low / acceptable: `#147A5B`
- Watch / caution: `#B4771E`
- High / stop: `#B54036`

## Typography

Primary:
- Inter / system sans-serif
- tight display tracking
- regular-to-semibold weights

Technical metadata:
- ui-monospace / SFMono / Menlo / Consolas
- uppercase only for labels, IDs and state metadata

Rules:
- avoid decorative serif pairings
- avoid tiny functional text below 11 px
- no headline that could belong to any startup

## Shape and depth

- default radius: 0–2 px
- controls may use 2–4 px for accessibility
- avoid pill-shaped containers except true status labels
- prefer borders and spacing over shadows
- hard offset shadow allowed only for diagrams / instruments
- no glassmorphism
- no decorative gradients

## Layout

- 40 px engineering grid may be used in backgrounds
- sections should have a single dominant idea
- major sections use horizontal rules as structure
- avoid grids where every child looks equally important
- allow whitespace to create hierarchy

## Interaction

- hover motion ≤ 4 px
- no autoplay movement
- route / process diagrams may use subtle directional motion only when useful
- respect `prefers-reduced-motion`
- interactive tools update consequence immediately

## Copy

Voice:
- calm
- specific
- evidence-led
- operational
- no hype

Preferred:
- “Working prototype”
- “Public-safe case study”
- “Illustrative model”
- “Known limitation”
- “Not yet validated”

Avoid:
- “Revolutionary”
- “Game-changing”
- “Enterprise-ready” unless evidenced
- invented ROI / testimonial language

## Evidence labels

Use these consistently:
- VERIFIED
- ILLUSTRATIVE
- ASSUMPTION
- RUNTIME-DEPENDENT
- NOT YET VALIDATED
- CONFIDENTIAL / OMITTED

## Anti-references

Do not drift toward:
- purple/blue AI gradients
- glass cards
- card-inside-card layouts
- floating blobs
- fake terminal screens
- excessive rounded containers
- status-chip soup
- fake logos / client strips
- anonymous testimonials
- unsupported percentages
